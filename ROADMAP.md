# YUI — Development Roadmap

*[日本語版](ROADMAP.ja.md)*

This document is a handoff brief for whoever (a human contributor or an AI coding agent) implements this project next. `architecture.md` is the source of truth for *what* to build and *why*; this document is about *in what order* and *under what ground rules*, given what already exists in the repository today.

---

## 1. Ground Rules (apply regardless of which agent/tool is doing the work)

- **`architecture.md` is authoritative.** If an implementation detail isn't covered there, propose an addition to `architecture.md` (and `architecture.ja.md`) rather than silently deciding unilaterally on a divergent design.
- **`AGENTS.md` conventions still apply**, independent of which AI tool is used: always respond to the human developer in Japanese, use relative paths only (no absolute paths, no `file:///` links), follow CalVer versioning (`YYYY.MM.RELEASE`), and describe user-visible changes in `CHANGELOG.md` / `CHANGELOG.ja.md` (`Unreleased`). How to contribute is in `CONTRIBUTING.md`.
- **Do not introduce a new DSL.** Section 6.2 already decided against a custom rendering/selection language; representation and selection are Python-API-driven (`Selector`/`Representation`). Section 14.3 extends the same rule to the AI chat assistant's tool-calling.
- **Do not implement force-field optimization/docking/DSSP/interaction-detection in-house inside this repo.** Those belong to the separate `proteindf-bridge` project (Chapter 10) — see Section 2 below on how to proceed while it doesn't exist yet.
- **Definition of done for any phase/task:** `cargo check --workspace`, `cargo test --workspace`, `cargo fmt --all -- --check`, and `cargo clippy --workspace --all-targets -- -D warnings` (as verified by `scripts/check.sh`) pass, and `scripts/check.sh --trunk` passes locally before the pull request is opened, with its summary written in the pull request (GitHub Actions CI also runs the same checks on every pull request); if a design decision was made or changed, `architecture.md`/`architecture.ja.md` are updated in the same change.
- **Commit messages are English**, regardless of which tool authored them.
- **Branching model is git-flow.** `main` holds only released, tagged states (CalVer, e.g. `2026.9.0`) and is updated exclusively by merging a `release/*` or `hotfix/*` branch — never push feature work to `main` directly. `develop` is the integration branch: every `feature/*` branch (e.g. `feature/phase-5b1-spatial-partitioning`) is created from `develop` and its PR targets `develop`, not `main`. When a release is prepared, branch `release/<CalVer>` from `develop`, finish it there, then merge into both `main` (tagged) and back into `develop`. Urgent post-release fixes use `hotfix/*` branched from `main`, merged into both `main` (as a new release) and `develop`. `AGENTS.md`/`ROADMAP.md`/`ROADMAP.ja.md` are living documents maintained on `develop`; `main`'s copies reflect whatever was current at the last release.

## 3. Phased Plan

Phases are ordered by dependency, following the same build-up `architecture.md` itself uses (foundational chapters first, advanced/value-add features last). Each phase should be small enough to land as one or a few reviewable changes; don't try to do a whole phase in one giant commit.

### Phase 1 — Harden `core` + local `AtomGroup`/`Selector` stand-in (Complete)
- Bring `core`'s `AppState` in line with §2.1 (lossless Rust ⇄ MessagePack ⇄ YAML round-trip), with tests for each conversion direction.
- Add a minimal, local `AtomGroup` (chain → residue → atom tree, §2.2) and a `Selector` with the `Select_*` predicates plus `And`/`Or`/`Not` (§6.2.1) *inside `core` for now*, clearly marked as a temporary stand-in for `proteindf-bridge`. Do not build out format parsers (PDB/mmCIF/etc.) here — that belongs to `proteindf-bridge`; a hand-built or trivially-parsed test fixture is enough to unblock rendering/UI work.
- Add `Representation` (§6.2.2) as a structured type in `AppState`.

### Phase 2 — `frontend` MVP: visible rendering (Complete)
- `iced::widget::pane_grid` skeleton matching §8's Left/Center/Right/Bottom layout (panels can be placeholders except Center).
- `wgpu` geometry instancing for ball-and-stick (§4.1) rendering the Phase-1 stand-in structure, natively, with no networking yet.
- Goal: a demoable "load a small structure, see it rendered, rotate/zoom the camera" milestone.

### Phase 3 — Scripting surface (Complete)
- `PyO3` native bindings exposing `Selector`/`Representation` per §6.1 (`yui.select(...).show(...).color_by(...)`).
- This unblocks both QCLObot integration (Ch.11) and the AI chat assistant's tool-calling (§14.3) later, since both are defined in terms of this same Python API rather than a new one.

### Phase 4 — `backend` wiring: structure I/O + delta sync + roles (Complete)
- REST endpoints for structure upload/fetch; WebSocket delta-sync of `AppState` changes (§7.3) using `rmp-serde`.
- `CollabTransport` trait (§7.2) with the `WebSocketTransport` implementation; `RoleToken` validation per the Host/Editor/Viewer model (§7.1).
- Wire `frontend` to consume `backend` over this channel instead of (or in addition to) local file I/O.

### Phase 5 — Scale-out rendering (blocked on `proteindf-bridge` for full fidelity) (5a, 5b, 5c-i, 5c-ii and 5c-iv complete; 5c-iii not started)

Phase 5 covers a wide surface (§4.2–§4.5) and is split into three independently-landable sub-phases so each stays reviewable:

- **Phase 5a — Ribbon (cartoon) rendering (§4.3).** Self-contained: the Phase-1 stand-in `AtomGroup`/`Residue` already carries `secondary_structure`, so this needs no new upstream data. Also the first time `AppState.representations` actually drives what the viewport renders (previously the viewport always drew every atom as ball-and-stick, ignoring `representations` entirely).
- **Phase 5b — GPU-driven culling / spatial partitioning / LOD / streaming (§4.2).** An optimization for ~1M-atom scale; not meaningfully testable against the ~9-atom stand-in peptide without a larger synthetic structure first. Do after 5a. §4.2 itself bundles four distinct subsystems, so it is further split:
  - **Phase 5b-i — Large synthetic structure fixture + spatial partitioning (BVH/Octree) in `core`.** Foundational: culling, LOD determination, and selection hit-testing (§4.2) all depend on this, and it immediately replaces the O(n²) brute-force bond detection already present in `frontend/src/viewport.rs` (flagged during the Phase 2 review) with something that scales. No compute shader work yet — pure CPU-side data structure with benchmarks/tests proving both correctness and the complexity win.
  - **Phase 5b-ii — Compute-shader frustum culling + Indirect Draw (Complete).** Built on top of 5b-i's `AtomBvh` and view frustum extraction. Extracts 6 clipping planes from `view_proj`, runs WGSL Compute Shader (`cs_cull`) on bounding spheres, compacts surviving instances with atomic counters, and dispatches via `draw_indexed_indirect` without CPU readback stalls. Verified against synthetic protein lattices.
  - **Phase 5b-iii — Staged LOD (ball-and-stick close / impostor billboards medium) (Complete).** Built on top of 5b-ii's culling. Implemented 2-tier staged LOD: Near tier ($\le 65.0\text{ \AA}$) renders full geometry meshes for atom spheres and bonds; Mid tier ($> 65.0\text{ \AA}$) renders camera-facing billboard quad impostors with circular pixel discard and normal reconstruction, hiding bonds to minimize primitive pressure. `cs_cull` dynamically compacts surviving instances into Near and Mid buffers via distance-squared sorting, and dispatches dual `draw_indexed_indirect` pipelines. The third tier ("surface-only" at long range, §4.2) is documented as a gap until Phase 5c lands.
  - **Streaming (§4.2, chunk-based load/evict) is deferred indefinitely**, not scheduled as a numbered sub-phase. It requires `backend` support for paginated/chunked structure delivery, which doesn't exist, and there's no real large dataset yet exercising the full pipeline end-to-end to motivate it. Revisit once a real large-structure ingestion path exists (e.g. once `proteindf-bridge` can parse real large PDB/mmCIF files).
- **Phase 5c — Molecular surface & isosurface via Marching Cubes (§4.4/§4.5).** Split into four steps to ensure a verifiable CPU ground truth and progressive rendering integration:
  - **Phase 5c-i — CPU reference implementation in `core` (Complete).** Verifiable reference implementation of 3D Gaussian density grid generation and Marching Cubes isosurface extraction with shared-edge vertex welding, outward normal calculation, and nearest-atom ID mapping. Verified against analytical sphere fixtures (area/volume within ±5%), closed manifold topology, and 1HLS.
  - **Phase 5c-ii — Live rendering of `RepresentationKind::Surface` via CPU mesh (Complete).** Connect generated CPU surface meshes to the viewport rendering pipeline and `RepresentationKind::Surface`, supporting vertex coloring by `ColorScheme` (chain, residue, uniform).
  - **Phase 5c-iii — GPU (Compute Shader) porting.** Port the Marching Cubes isosurface extraction to WebGPU Compute Shaders, verified against the 5c-i CPU reference output for identical topology and geometry.
  - **Phase 5c-iv — Gaussian CUBE input (first version done).** `proteindf-bridge` 2026.10.5 added the CUBE reader; File → "Open CUBE (Isosurface)..." shows the positive and negative isosurfaces of the first dataset (`core/src/cube_iso.rs`, `frontend/src/cube_view.rs`). The Right-pane card has an isolevel slider, an orbital selector and color swatches; the CUBE's atoms are shown when no structure is open; oblique grids are resampled; the file path is saved in the workspace (`data_paths.cube_path`, native only). Not done yet: checking with a real ProteinDF CUBE, a relative path in the workspace, and reopening in the browser.

All three sub-phases need robust large-structure parsing and secondary-structure labels from `proteindf-bridge` (§10, §10.1) for real protein data; against the Phase-1 stand-in, implement against synthetic/test data first and re-validate once `proteindf-bridge` lands.

### Phase 6 — Terminal & Log Viewer, AI Chat Assistant (6a complete; 6b not started)

These are additive UI features on top of an already-working visualization + scripting core — do not start them before Phases 1–4 are functional, since they depend on the Role model (§7.1) and the Python API (§6) being in place for their access-control and tool-calling design to make sense. (This precondition is already satisfied as of Phase 4.) Chapter 13 and Chapter 14 are functionally independent of each other, so split into two sub-phases:

- **Phase 6a — Terminal & Log Viewer (Chapter 13).** Both hosted in `backend` per §13.2, with `frontend` talking to them over the same transport-abstraction pattern as collaboration (§7.2). Access-gated by the Role model (§7.1): Terminal defaults to Host-only, Log Viewer may be shared with Editor. The Terminal (real PTY spawning, ANSI/VT parsing via a VTE crate, a from-scratch custom `iced` cell-grid rendering widget) is substantially harder than the Log Viewer (reuses the existing delta-sync/streaming patterns from Chapter 7 for plain text lines), so split further:
  - **Phase 6a-i — Log Viewer (Complete).** `notify`-based file tailing with uncreated file waiting, append-only line streaming via `/api/logs` WebSocket endpoint, tabbed Bottom pane with bounded ring-buffer (5,000 lines) text view, auto-scrolling with pause/resume toggle, and substring filtering. Read-only; shareable with Editor role.
  - **Phase 6a-ii — Terminal (Complete).** `portable-pty` PTY sessions hosted in `backend` with shell spawning and full-duplex bidirectional streaming via `/api/terminal`; ANSI/VT state machine parsed with `vt100` crate (selected over `alacritty_terminal` for zero C dependencies, pure in-memory model, and WASM compatibility); custom `iced` terminal pane widget rendering monospace cell grid with cursor tracking and quick control-key buttons. Gated strictly to Host role (role_token=1) via `RoleResolver`.
- **Phase 6b — AI Chat Assistant (Chapter 14).** `LlmProvider` abstraction over Claude/Gemini/Ollama; chat panel; tool-calling onto the Phase-3 Python API; state-digest context grounding. Do after 6a. Note before starting: genuine end-to-end verification needs either real API credentials (Claude/Gemini) or a local Ollama install — decide up front whether to test with mocked HTTP responses only, or whether real credentials will be made available, since that materially changes what "done" looks like for this sub-phase.

### Phase 6c — WASM/Web Frontend Support (Complete)

`frontend` has been native-only through every phase so far; §1.1 states WASM compatibility as a goal, but no phase has actually attempted a browser build. Whether the existing wgpu/`iced::widget::shader`-based rendering (compute-shader culling, billboard impostors, custom ribbon/terminal pipelines) even runs in a browser at all is the biggest unknown, so prove that before adding networking:

- **Phase 6c-i — Minimal WASM build proving wgpu/iced render in a browser (Complete).** Separated native-only networking crates (`tokio-tungstenite`, native `tokio` runtime, `reqwest`) in `frontend/Cargo.toml` with `cfg(not(target_arch = "wasm32"))`, configured `getrandom_backend="wasm_js"` in `.cargo/config.toml`, created `frontend/index.html` Trunk entrypoint, and verified successful Trunk compilation and browser execution of the complete `wgpu` 3D rendering pipeline (ball-and-stick, ribbon/cartoon Catmull-Rom meshes, frustum culling, LOD, camera orbit/zoom). Stubbed networking into standalone local viewer mode with `console_error_panic_hook` and `web-sys` console logging.
- **Phase 6c-ii — WASM-compatible transport layer (Complete).** Implemented a `cfg(target_arch = "wasm32")` browser-WebSocket transport using `gloo-net`, bridged to `iced`'s `Send` stream requirements via `tokio::sync::mpsc` channels and `wasm_bindgen_futures::spawn_local`. Re-enabled target-independent `reqwest` backed by browser `fetch` for initial state retrieval. Implemented URL query parameter target extraction (`?collab=` / `?backend=`) with fallback to `location.hostname` (`resolve_wasm_collab_url`), fully reconnecting browser builds to live `backend` collaboration, log tailing, and bidirectional PTY terminal streams without branching high-level application logic.

Actually serving/deploying the built WASM bundle for end users stays under Phase 8 (§9); 6c only proves the capability works.

### Phase 6d — Menu Bar & Context Menus (§8.2–§8.4, new) (Complete)

Not blocked on anything beyond the already-working visualization + scripting core; adds discoverable UI for actions that today are only reachable via the Python console or hardcoded defaults. This is a newly-designed UI area (§8 previously only had three sparse bullets) rather than an implementation of a pre-existing spec, so it's split by what's buildable today vs. what needs a prerequisite widget built first — Left and Right panes are currently placeholder text, not interactive widgets:

- **Phase 6d-i — Top menu bar (File / View / Help, §8.2) (Complete).** Implemented an in-window `iced` widget (zero external crate dependencies) supporting native and WASM builds. File menu: New (reset to default empty `AppState`), Open (YAML state import), Save / Save As (YAML state export), and Quit. View menu: Reset Camera (`CameraState` restored to default via `camera_reset_token`), and show/hide toggle for Left (Explorer), Right (Inspector), and Bottom (Panels) panes via `build_pane_configuration`. Help menu: About modal displaying CalVer version, GPLv3 license, and project description. Edit menu explicitly deferred per spec until history tracking exists. All menu actions route through existing `AppState` / `CameraState` pipelines without creating a custom DSL (§8.4).
- **Phase 6d-ii — 3D viewport right-click context menu (§8.3) (Complete).** Implemented ray-cast atom picking using `math::screen_to_world_ray` and `AtomBvh::query_ray` (Slab-method AABB broad-phase pruning with atom radius margins, followed by exact ray-sphere nearest positive intersection testing). Integrated right-click event handling in `viewport::ViewportProgram` to publish context menu targets to the main application loop. Built an in-window context menu card widget (`context_menu::view_context_menu`) on the top stack layer backed by a transparent `mouse_area` backdrop that dismisses on outside clicks. Adhered strictly to §8.4 by routing all menu actions (Select Atom, Select Residue, Hide Atom, Show As, Color By) directly to `Selector::AtomIds`, `Selector::ResidueRange`, and `Representation` modifications with live viewport feedback (selection highlights, custom color overrides, and hidden atom culling). Tested across native and WASM builds.
- **Phase 6d-iii — Pane/view model generalization (foundation, precedes 6d-iv/6d-v) (Complete).** Decoupled "which content is docked where" from the fixed `PaneKind` enum by introducing runtime `ViewId` enumeration (`Viewport`, `StructureTree`, `RepresentationInspector`, `LogViewer`, `PythonConsole`, `Terminal`, `AiChat`) and `PaneViewState` (views list + active index) for each pane. Generalized the tab switcher UI (`view_tab_bar`) to render dynamically on any pane containing multiple views, seamlessly unifying the former `bottom_tab` into the generic pane view model while maintaining 100% visual and behavioral regression-free layout for single-view panes. Extended `state.yaml` persistence (`SavedWorkspaceState`) to serialize per-pane open/active views alongside `AppState` with automatic fallback to standard defaults when loading legacy YAML files. Covered with 4 unit tests and verified across native and WASM builds.
- **Phase 6d-iv — Left pane becomes a real structure/file tree, plus its context menu (Complete).** Implemented interactive `StructureTree` widget in `frontend/src/structure_tree.rs` registered as `ViewId::StructureTree`. Recursively visualizes `AtomGroup` hierarchy (Model → Chain → Residue → Atom) with configurable indentation and expand/collapse toggles. Guaranteed default-collapsed state for safe handling of large structures (e.g. 9,216-atom synthetic lattice). Strictly followed §8.4 action pipeline: left-clicking nodes triggers instant selection highlights (`Selector::PathWildcard` for Model, `Selector::ResidueRange` for Chain/Residue, `Selector::AtomIds` for Atom) rendered with yellow uniform color. Provided right-click context menu (`view_tree_context_menu`) on top stack layer with Select, Hide, Show As (Ball & Stick, Spacefill, Cartoon), and Color By (Element, Chain, Residue, Uniform) options directly manipulating `self.state.representations`. Supported empty state handling when no structure is loaded. Verified across native and WASM builds with 6 comprehensive unit tests.
- **Phase 6d-v — Right pane becomes a real `Representation` list widget, plus its context menu (Complete).** Implemented interactive `RepresentationInspector` widget in `frontend/src/representation_inspector.rs` registered as `ViewId::RepresentationInspector`. Directly renders and manipulates `self.state.representations` as an interactive card list with real-time viewport feedback. Features "+ Add" toolbar button for creating default representations (`Selector::All`, `BallAndStick`, `ColorScheme::Element`), per-row visibility toggle buttons (`👁`/`🚫`), representation removal (`✕`), and button-group selectors for representation kinds (`BallAndStick`, `Cartoon`, `Cpk`, `Licorice`, `Line`, with explicit "(not yet rendered)" tag for `Surface`) and color schemes (`Element`, `Chain`, `Residue`, `SecondaryStructure`, `Uniform`). Included right-click context menu (`view_rep_context_menu`) on top stack layer offering Visibility Toggle, Show As, Color By, and Delete actions. Verified across native and WASM builds with 4 comprehensive unit tests.

All five sub-phases must route their actions through the same `Selector`/`Representation` Python-API-equivalent calls as the scripting layer (§8.4) — no menu- or context-menu-specific command path, consistent with the no-new-DSL rule (§6.2).

### Phase 6e — Replace the local `AtomGroup`/`Selector` stand-in with real `proteindf-bridge` (unblocks Phase 5c and Phase 7) (Complete)
Investigated 2026-09-19: this was always the plan (`core/src/atom_group.rs` and `selector.rs` are explicitly documented as "temporary local stand-ins... until proteindf-bridge is implemented"), and real `proteindf-bridge` already has a working, documented "protein schema" convention (`/model_N/chain_id/res_key/atom_key` path depth, exactly mirroring this repo's typed `Model → Chain → Residue → AtomRecord`) plus a `Bond::setup()` VDW-radius detector — so bond generation belongs entirely on the `proteindf-bridge` side; this repo should only consume it, never reimplement detection logic locally (§10). A direct type swap (not a converting adapter layer) is the right shape, but the blast radius is real: 14 files read the typed `.models`/`.chains`/`.residues`/`.atoms` fields directly (`core/src/{selector,atom_group,packing,spatial,export}.rs`, `core-py/src/{state,atom_group}.rs`, `frontend/src/{ribbon,structure_tree,menu_bar,state_sync,viewport}.rs`, `backend/src/main.rs`, `renderer-native/src/main.rs`), so this is split into dependency-ordered sub-phases rather than one PR. Breaks `state.yaml`/MessagePack backward compatibility for any file carrying real `atom_group` data — no `#[serde(default)]` can bridge a full type swap, so 6e-vii must give `AppState.version` real meaning (a clear "unsupported/legacy format" error) instead of leaving it a decorative counter.

**Branching exception (decided 2026-09-19, while reviewing 6e-ii):** Ground Rule §1 requires
`cargo check --workspace` to pass as the definition of done for *any* phase/task, but this sub-phase
split necessarily leaves other, not-yet-migrated files broken between 6e-ii and 6e-v (that's the whole
point of splitting a 14-file blast radius into reviewable increments). Merging each sub-phase straight
into `develop` would leave `develop` itself failing `cargo check --workspace` for the whole span of
Phase 6e, violating that rule for every other concurrent contributor. Resolution: 6e-ii through 6e-v are
**not merged into `develop` individually.** Each sub-phase branches from the *previous* sub-phase's
branch (a stacked-PR chain: `feature/phase-6e-iii-...` branches from `feature/phase-6e-ii-atomgroup-swap`,
not from `develop`; its PR's base branch is the previous sub-phase's branch, not `develop`), and gets
reviewed/approved individually on that basis. Only once 6e-v lands and `cargo check --workspace` /
`cargo test --workspace` are green again does the whole stack get merged into `develop`, sub-phase by
sub-phase in order (oldest first), each merge now a fast-forward with no new breakage introduced.
6e-i is exempt (already merged into `develop` — it never broke the workspace on its own).

### Phase 6f — VSCode-style project explorer with a generic text editor (Complete)
`architecture.md` §1.1 already anticipated "future views such as a script editor" when Phase 6d-iii generalized pane content into runtime `ViewId`s. This phase implements that: browsing a chosen project directory as a tree (reusing the Left pane's existing "Explorer / Playbook" tab strip, alongside `StructureTree`), and opening a selected file in whichever viewer fits it — a new generic text editor by default, or an existing structure/state viewer when the extension matches one, with the user able to override the choice when more than one applies. Split into dependency-ordered sub-phases so each PR stays reviewable.

**Design corrections found before kickoff (2026-09-23):** the original split assumed `rfd::AsyncFileDialog` alone would cover directory *browsing* the same way it covers single-file open/save — it doesn't. On wasm32, `FileHandle` from `pick_folder()` is an opaque reference with no `path()` and no listing capability (`path()` "does not exist in WASM32" per rfd's own docs); enumerating a folder's contents client-side would need the browser's separate File System Access API, which Firefox and Safari don't implement at all (Chromium-only, confirmed as of Sept 2026) — a real dead end for a cross-browser tree. The fix: browse via the existing `backend` server instead of the browser's local filesystem. `backend` already runs with full native `std::fs` access and already has an analogous env-var-scoped filesystem convention (`YUI_LOG_ROOT` for the log-streaming feature) to model a new `YUI_WORKSPACE_ROOT` on — a REST endpoint under that root works identically for native and wasm32 clients (both just issue HTTP requests, same as the rest of this app's collab/REST layer), sidestepping the browser API gap entirely rather than accepting it as permanent. Native builds keep a `rfd::pick_folder()`-plus-local-`std::fs` fallback for standalone use with no backend connected. Separately, "route structure files into the existing 3D-viewport/`AtomGroup` pipeline" turned out not to describe anything that exists yet — the only code that loads a real PDB/mmCIF file into an `AtomGroup` lives in `core/tests/real_pdb_validation.rs` (test-only), never reachable from the running app. That's carved out into its own small sub-phase rather than left as an assumed dependency of the dispatch phase.

- **Phase 6f-i (Complete) — Generic text editor pane.** A new `ViewId::TextEditor` backed by `iced::widget::text_editor`, opening/saving arbitrary files via `rfd::AsyncFileDialog`, deliberately chosen over hand-rolled platform-specific I/O because it supports both native (OS-native dialogs) and wasm32 (browser `<input type=file>` under the hood) through the same async API for single-file open/save — one implementation, not two. Native `FileHandle`s carry a real path (so "Save" can write back without prompting); wasm32 `FileHandle`s do not (browser security model), so "Save" degrades to "Save As" behavior there — an accepted platform difference, not a bug. Its own Open/Save controls stay local to the pane, deliberately not wired into the existing File-menu Open/Save (§8.2), which remains specific to `state.yaml` workspace state.
- **Phase 6f-ii (Complete) — Backend filesystem endpoints.** New `GET /api/fs/list?path=<relative>` and `GET /api/fs/read?path=<relative>` REST endpoints, scoped to a `YUI_WORKSPACE_ROOT` env var (default: CWD) the same way `create_shared_state()` already scopes log streaming to `YUI_LOG_ROOT`. Every `path` is resolved relative to that root, canonicalized, and verified to still fall under the root's prefix before touching disk (reject otherwise) — this is a server endpoint reachable by any connected client, not a single local user's own machine, so path-traversal defense is not optional. Gate behind `RoleResolver` at a level consistent with its information-disclosure risk (reusing the existing Host/Editor/Viewer model — err toward requiring at least Editor, not open to Viewer, pending a closer look at existing role semantics for read-only-but-sensitive endpoints). No frontend UI yet.
- **Phase 6f-iii (Complete) — Project directory tree (native + wasm32, unified).** A new tab in the Left pane's "Explorer / Playbook" tab strip (alongside the existing `StructureTree`, reusing its expand/collapse tree-row UI pattern). When a backend is connected, browses `/api/fs/list` under its configured `YUI_WORKSPACE_ROOT` — no folder-picker dialog needed (or meaningful, since the root lives on a possibly-remote server), works identically for native and wasm32 clients since both just do HTTP. When running standalone with no backend, falls back to `rfd::AsyncFileDialog::pick_folder()` plus local `std::fs::read_dir` (native only; standalone wasm32 gets no tree, since it has neither a backend nor local filesystem access). Expand-on-demand in both cases (lazy per-node, not a full recursive walk at open-time) to avoid hanging on large real directories the synthetic `StructureTree` fixtures never had to worry about; tolerate per-entry permission errors and symlink cycles without crashing. Emits a "file selected" event on click; does not yet decide what opens it (that's 6f-v).
- **Phase 6f-iv (Complete) — Load a real structure file into `AppState`.** Wires `proteindf_bridge`'s PDB/mmCIF loaders (`Pdb::from_file()` → `get_atomgroup()` → `AtomGroup::setup()`, the same pipeline `core/tests/real_pdb_validation.rs` already exercises in tests) into an app-reachable function that populates `AppState.atom_group`/`secondary_structure_map` from file bytes (sourced either from a local path or from a 6f-ii `/api/fs/read` response) and calls `sync_molecule_from_atom_group()` — today this path has never been reachable from the running UI, only synthetic fixtures ever get loaded. No UI entry point of its own yet; 6f-v calls it.
- **Phase 6f-v (Complete) — "Open with" dispatch.** Routes a file selected in 6f-iii to a handler by extension: a sensible default (structure files such as `.pdb`/`.cif`/`.mol2` go through 6f-iv's loader; anything else opens in the 6f-i text editor), with a picker the user can use to override the default when more than one handler applies to a given extension (e.g. `.yaml` could be a workspace `state.yaml` import or plain text).

## 5. Explicit Non-Goals (don't build these here)

- Force-field optimization, docking, or any full molecular-modeling engine — integrate external tools via `ModelingProvider` (Chapter 3) instead.
- A custom selection/rendering/chat command DSL — always route through the `Selector`/`Representation`/Python-API surface (§6.2, §14.3).
- PDB/mmCIF/MOL2/etc. format parsers, DSSP-equivalent secondary-structure estimation, or non-covalent interaction detection — these belong to `proteindf-bridge` (Chapter 10), not this repository.
